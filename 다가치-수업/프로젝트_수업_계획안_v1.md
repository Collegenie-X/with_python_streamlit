# AI 바이브 코딩 프로젝트 수업 계획안

> **한 줄 요약** : 코드를 외우는 수업이 아니라, **"내가 진짜 쓸 서비스"를 AI랑 같이 만들어보는 수업**이다.

---

## 수업 기본 정보

| 항목 | 내용 |
|---|---|
| **대상** | 중학교 2학년 |
| **총 시간** | 2시간 x 4일 = **8시간** |
| **팀 구성** | 5명이 한 팀 (역할을 나눠서 하나의 프로젝트를 함께 완성) |
| **도구** | Python + Streamlit + AI 코딩 도구 |
| **수업 방식** | 선생님이 알려주는 강의가 아니라, **팀이 직접 만들면서 배우는 방식** |

---

## 이 수업에서 제일 중요한 것

### "코딩을 배우는 게 아니라, 만드는 과정을 배운다"

AI가 코드를 대신 짜주는 시대가 왔다. 그러면 사람은 뭘 해야 할까?

```
AI가 잘하는 것                    사람이 해야 하는 것
─────────────────────          ─────────────────────
코드 작성                        "뭘 만들지?" 정하기
에러 수정                        "누가 쓸 건데?" 생각하기
반복 작업                        "이거 쓰기 불편한데?" 판단하기
빠른 검색                        "왜 이걸 만들어야 하지?" 이유 찾기
```

> **바이브 코딩** = AI에게 "이런 거 만들어줘"라고 말로 설명하고, 결과를 보고, "여기 좀 고쳐줘"라고 다시 말하는 개발 방식.
> 코드를 한 줄씩 외워서 치는 게 아니라, **내가 원하는 걸 정확히 설명하는 능력**이 핵심이다.

---

## 만드는 과정은 딱 4단계다

이 4단계를 한 바퀴 돌려보는 게 이 수업의 진짜 목표다.

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                  │
│   1단계. 정하기     →  "누구한테, 어떤 문제를 풀어줄 건데?"     │
│                        (한 줄로 정리할 수 있어야 한다)           │
│                                                                  │
│   2단계. 그리기     →  "화면이 어떤 순서로 넘어가?"             │
│                        (종이에 손으로 그려본다)                  │
│                                                                  │
│   3단계. 만들기     →  AI에게 설명해서 코드를 받는다             │
│                        (바이브 코딩)                             │
│                                                                  │
│   4단계. 고치기     →  직접 써보고 불편한 곳을 찾아 고친다       │
│                        (이게 진짜 실력이다)                      │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘

       사람이 한다           사람이 한다          AI가 한다           사람이 한다
       ──────────           ──────────          ─────────           ──────────
       1단계 정하기          2단계 그리기         3단계 만들기         4단계 고치기
```

> 4단계 중 AI가 하는 건 **3단계 하나뿐**이다.
> 나머지 3개는 전부 사람이 한다. 그래서 "코딩 실력"보다 **"생각하는 힘"**이 더 중요하다.

## 서버가 필요할까? — 프로젝트 시작 전에 꼭 판단해야 하는 것

```
질문 : "이건 나만 쓸 건가, 여러 명이 같이 쓸 건가?"

나만 쓴다                              여러 명이 같이 쓴다
────────                              ──────────────────
→ 서버 필요 없음                       → 서버 필요함
→ 내 컴퓨터에서 돌리면 끝              → 인터넷에 올려야 함 (배포)
→ 예 : 공부 타이머, 가계부              → 예 : 설문 조사, 급식 별점
```

> 이 판단을 **팀이 스스로 내리는 것**이 중요하다.
> "서버"라는 게 뭔지 몰라도 된다. "다른 사람 데이터를 모아야 하면 서버가 필요하다" — 이것만 알면 된다.

## 활동 세부계획

### 1회차 : OT — "왜 만드는가" 이해하기 (2시간)

| 시간 | 활동 | 구체적으로 하는 것 |
|---|---|---|
| 0:00~0:20 | **팀 만들기** | 5명이 한 팀. 역할 정하기 (PM / 기획 / 화면 / 데이터 / 발표). 서로 이름 익히고 분위기 만들기 |
| 0:20~0:50 | **"AI 시대에 사람은 뭘 해야 할까?" 이야기** | AI가 코드를 다 짜준다면, 우리는 뭘 잘해야 하나? → "뭘 만들지 정하는 능력"이 가장 중요하다는 걸 깨닫기. "만드는 4단계(정하기→그리기→만들기→고치기)" 배우기 |
| 0:50~1:10 | **"서버가 필요할까?" 토론** | 실제 앱 예시 보면서 판단 연습. 카카오톡은? 계산기는? 인스타는? → "여러 명 데이터를 모으려면 서버가 필요하다" 기준 세우기 |
| 1:10~1:40 | **바이브 코딩 라이브 데모** | 선생님이 AI한테 "급식 별점 앱 만들어줘"라고 말하면 5분 만에 진짜 앱이 나오는 걸 눈으로 확인. "와, 이게 되네?" 하는 순간이 중요 |
| 1:40~2:00 | **팀 프로젝트 주제 정하기** | 아이디어 10개 중에서 우리 팀 주제 고르기. **한 줄 기획서** 쓰기 : "○○가 / ○○ 때문에 불편해서 / ○○를 만든다" |

**이 날 끝나면 손에 있는 것 :**
- 팀 역할표
- 한 줄 기획서 (누가 / 왜 / 뭘 만드는가)
- 서버 필요 여부 판단 결과

**준비물 :** 노트북 또는 태블릿, A4 종이, 필기도구

---

### 2회차 : 설계 — "어떻게 흘러가는지" 그리기 + 첫 화면 (2시간)

| 시간 | 활동 | 구체적으로 하는 것 |
|---|---|---|
| 0:00~0:30 | **화면 흐름 그리기** | 종이에 화면을 네모로 그리고 화살표로 연결. "시작 화면 → 입력 화면 → 결과 화면" 이런 식으로. 이게 **알고리즘의 시작**이다. 복잡한 코드가 아니라, "어떤 순서로 흘러가는지" 정리하는 게 알고리즘 |
| 0:30~0:50 | **데이터 구조 정하기** | "우리 앱에서 저장해야 하는 정보가 뭐지?" 정리. JSON이라는 형식으로 데이터를 정리하는 법 배우기. 예 : `{"이름": "비빔밥", "별점": 4, "코멘트": "맛있었어"}` |
| 0:50~1:30 | **바이브 코딩 : 첫 화면 만들기** | AI한테 "우리 앱의 시작 화면을 만들어줘. 제목이 있고, 시작 버튼이 있어"라고 설명 → 코드를 받고 → 실행해보고 → "버튼 색 바꿔줘" 다시 요청. 이 **"설명 → 확인 → 수정 요청"** 사이클을 몸으로 익히기 |
| 1:30~1:50 | **Streamlit 핵심 기능 체험** | 버튼(st.button), 선택지(st.radio), 슬라이더(st.slider), 입력칸(st.text_input) — 이 4개만 알면 웬만한 앱은 만들 수 있다 |
| 1:50~2:00 | **팀 회고** | "오늘 된 것 / 안 된 것 / 다음에 할 것" 3가지만 정리 |

**이 날 끝나면 손에 있는 것 :**
- 종이에 그린 화면 흐름도 (= 우리 앱의 설계도)
- JSON 데이터 구조
- 실제로 돌아가는 첫 화면 1개

**준비물 :** 1회차 기획서, A4 종이(스케치용), 노트북

> **여기서 배우는 것** : "알고리즘"이란 거창한 게 아니라, **"이 다음에 뭐가 나올까?"를 정해놓는 것**이다.
> 화면 흐름을 그리는 순간, 이미 알고리즘을 만들고 있는 거다.

---

### 3회차 : 개발 — 진짜 만들기, 팀으로 합치기 (2시간)

| 시간 | 활동 | 구체적으로 하는 것 |
|---|---|---|
| 0:00~0:50 | **팀원별로 나눠서 만들기** | 화면 흐름도에서 각자 맡은 부분을 AI한테 설명해서 코드 만들기. 화면 담당은 디자인, 데이터 담당은 저장/계산 로직, 기획은 콘텐츠(질문, 스토리 등) 작성 |
| 0:50~1:20 | **하나로 합치기** | 각자 만든 화면을 하나의 앱으로 연결. "시작 화면에서 버튼 누르면 다음 화면으로 넘어가게" 해주는 게 session_state. 여기서 막히면 AI한테 "두 화면을 연결해줘"라고 요청 |
| 1:20~1:40 | **직접 써보고 버그 잡기** | 처음부터 끝까지 한 번 돌려본다. 안 되는 거, 이상한 거 목록 만들기 → AI한테 "이거 왜 안 돼?" 물어보기 → 고치기. **이 "써보고 → 문제 찾고 → 고치는" 과정이 프로처럼 일하는 방식** |
| 1:40~1:50 | **다른 팀한테 보여주기** | 지금까지 만든 거 간단히 시연. 다른 팀 피드백 듣기 ("이 부분 헷갈려", "버튼이 안 눌려") |
| 1:50~2:00 | **팀 회고** | "내일 마무리할 것" 리스트 작성 |

**이 날 끝나면 손에 있는 것 :**
- 처음부터 끝까지 한 번은 돌아가는 앱 (MVP = 최소 기능 제품)

**준비물 :** 2회차 화면 흐름도, 각자 맡은 역할 확인

> **여기서 배우는 것** : 처음부터 완벽하게 만드는 사람은 없다.
> **"일단 만들고 → 써보고 → 고치고"를 반복하는 게 진짜 개발**이다.
> 이걸 한 바퀴 돌려본 경험이, 코딩 문법 100개 외운 것보다 훨씬 강력하다.

### 4회차 : 완성 — 예쁘게 다듬고, 세상에 내놓기 (2시간)

| 시간 | 활동 | 구체적으로 하는 것 |
|---|---|---|
| 0:00~0:30 | **UI 다듬기** | "사용자가 처음 봤을 때 뭘 해야 하는지 바로 알 수 있는가?" 관점으로 점검. 색상, 글씨 크기, 버튼 위치, 이모지 추가. AI한테 "이 화면을 더 보기 좋게 바꿔줘"라고 요청 |
| 0:30~0:50 | **배포하기** | Streamlit Cloud에 앱 올리기 → URL 나옴 → QR코드 만들기 → 친구한테 보내서 진짜로 써보게 하기. "내가 만든 게 인터넷에 올라갔다!" 이 순간이 가장 중요 |
| 0:50~1:05 | **발표 준비** | 발표 구조 정리 : ① 왜 만들었는가 (문제) → ② 어떻게 만들었는가 (시연) → ③ 만들면서 뭘 배웠는가 (배운 점). 이 3개만 말하면 된다 |
| 1:05~1:45 | **팀 발표회** | 각 팀 3분 발표 + 질문. 다른 팀 앱도 직접 써본다 |
| 1:45~2:00 | **다음 단계 안내** | 이 수업은 끝이 아니라 시작. 방학 때 프로젝트 2번째를 만들면, 고등학교 때 포트폴리오가 된다. "중2에 시작해서 고2까지 프로젝트 3개 쌓는 로드맵" 안내 |

**이 날 끝나면 손에 있는 것 :**
- 인터넷에 배포된 앱 (URL + QR코드)
- 팀 발표 경험
- 포트폴리오로 쓸 수 있는 프로젝트 1개

**준비물 :** 3회차까지 만든 앱, 발표용 메모

> **여기서 배우는 것** : "만드는 것"과 **"세상에 내놓는 것"**은 완전히 다른 경험이다.
> 배포하고, 다른 사람이 쓰는 걸 보는 순간 — "아, 이렇게 만들면 안 되는구나" 또는 "와, 진짜 쓴다!" — 이 감각이 교과서에서는 절대 못 배우는 것이다.

## 팀 역할 (5명이 하나의 프로젝트를 만든다)

| 역할 | 하는 일 | 한마디로 |
|---|---|---|
| **PM** (진행자) | 시간 관리, 팀원 의견 조율, "지금 뭐 해야 하지?" 정해주기 | 감독 |
| **기획** | 질문/스토리/콘텐츠 설계, 한 줄 기획서 관리 | 작가 |
| **화면 담당** | 앱이 예쁘게 보이도록 레이아웃, 색상, 배치 다듬기 | 디자이너 |
| **데이터 담당** | 점수 계산, 저장/불러오기, 차트 만들기 | 엔지니어 |
| **발표 담당** | 매번 뭘 했는지 기록, 최종 발표 준비 및 발표 | 스피커 |

> 역할은 "책임 영역"이지, **코딩 면제가 아니다.**
> 바이브 코딩은 5명 전원이 직접 한다. 역할에 상관없이 AI한테 직접 말하고, 결과를 보고, 수정 요청하는 경험을 한다.

## 팀이 고를 수 있는 프로젝트 아이디어 10개

| 번호 | 프로젝트 | 한 줄 설명 | 서버 필요? |
|---|---|---|---|
| 1 | **감정 방탈출 게임** | 감정 입력하면 스토리가 달라지는 텍스트 게임 | 아니오 |
| 2 | **학교 설문 리서치 툴** | 설문 만들고 → 응답 받고 → 차트로 결과 보기 | 예 |
| 3 | **취향 추천 테스트** | 질문 5개 답하면 나한테 맞는 웹툰/노래 추천 | 아니오 |
| 4 | **급식 별점 리뷰판** | 오늘 급식 별점 매기고 이달의 TOP 메뉴 랭킹 보기 | 예 |
| 5 | **공부 타이머** | 뽀모도로 타이머 + 과목별 공부시간 그래프 | 아니오 |
| 6 | **AI 과목 튜터** | "이 문제 어떻게 풀어?" 물으면 단계별로 알려주는 챗봇 | 아니오 |
| 7 | **플레이리스트 추천기** | 지금 기분 고르면 어울리는 노래 리스트 추천 | 아니오 |
| 8 | **용돈 가계부** | 지출 기록 → 카테고리별 차트 → AI 소비 피드백 | 선택 |
| 9 | **시간표 알리미** | 요일별 시간표 + "내일 준비물" 알림 | 예 |
| 10 | **환경 데이터 대시보드** | 기온/미세먼지 데이터 차트 + AI 해석 코멘트 | 아니오 |

> 어떤 아이디어를 골라도, **만드는 과정(정하기→그리기→만들기→고치기)은 똑같다.**
> 그 과정을 한 바퀴 돌려보는 게 이 수업의 핵심이다.

## 이 수업은 왜 "바이브 코딩"으로 하는가?

### 기존 코딩 수업과 이 수업의 차이

| 기존 코딩 수업 | 이 수업 |
|---|---|
| `print("Hello")` 치는 법 배움 | **진짜 돌아가는 앱** 1개 완성 |
| `if/else` 문법 암기 | "정하기→그리기→만들기→고치기" **전체 과정** 경험 |
| 정답이 정해진 문제 풀기 | **정답이 없는 문제**를 스스로 정의하고 해결 |
| 혼자 하는 숙제 | **5명이 팀으로** 하나의 프로젝트 완성 |
| 수업 끝나면 남는 게 없음 | **인터넷에 배포된 앱 URL**이 남음 |
| AI가 대체할 수 있는 스킬 | AI를 **도구로 쓰는** 스킬 |

### AI 시대 프로젝트는 이렇게 만든다

```
[과거]  문법 공부 → 코드 타이핑 → 디버깅 → 완성 (몇 달 걸림)

[지금]  문제 정의 → AI에게 설명 → 결과 확인 → 수정 요청 → 완성 (몇 시간이면 됨)
        ─────────   ──────────   ──────────   ──────────
         사람          사람         사람         사람
                    (AI가 코드를 짜줌)
```

> 달라진 건 "코드를 누가 짜느냐"이고, 달라지지 않은 건 **"뭘 만들지 정하는 건 사람"**이라는 것.
> 그래서 이 수업은 코드를 가르치지 않고, **"정하고, 그리고, 확인하고, 고치는 과정"**을 가르친다.

## 평가 방법

### 점수가 아니라 "성장 과정"을 본다

| 보는 것 | 구체적으로 |
|---|---|
| **기획서** | "누가 / 왜 / 뭘 만드는가"를 한 줄로 정리했는가? |
| **화면 흐름도** | 종이에 그린 설계도가 논리적으로 이어지는가? |
| **중간 과정** | "안 되는 것"을 발견하고 "고치려고 시도"했는가? |
| **완성 앱** | 처음부터 끝까지 한 번은 돌아가는가? |
| **팀 발표** | "왜 → 시연 → 배운 점"을 3분 안에 전달했는가? |

> **완벽하게 만들었느냐가 아니라, 4단계를 한 바퀴 돌렸느냐를 본다.**
> 버그가 있어도 괜찮다. "왜 이게 안 되는지 알고 있다"가 "완벽하지만 왜 되는지 모른다"보다 훨씬 낫다.

### 최종 발표 형식

```
3분 발표 = 이 3가지만 말하면 된다 :

  ① 왜 만들었나?     →  "○○가 불편해서 / ○○를 해결하려고"
  ② 어떻게 만들었나?  →  앱을 직접 돌려서 보여주기 (라이브 시연)
  ③ 뭘 배웠나?       →  "이게 어려웠는데 이렇게 해결했다"
```

## 이 수업이 끝난 다음에는?

이 수업은 "끝"이 아니라 **"시작"**이다.

```
프로젝트 1 (이 수업, 중2)
  → 8시간 만에 앱 1개 완성
  → "나도 만들 수 있구나" 자신감

      ↓

프로젝트 2 (방학, 중3)
  → 4주간 더 깊이 만들기
  → 친구 20~100명이 실제로 쓰는 서비스
  → 피드백 받고 개선하는 경험

      ↓

프로젝트 3 (고등학교)
  → 3~6개월 제대로 만들기
  → 사용자 500명+, 수익 발생 시도
  → 대입 포트폴리오의 핵심 소재
```

> 2032년 대입에서는 "시험 점수"만이 아니라 **"내가 뭘 만들었고, 어떻게 성장했는가"**를 본다.
> 이 수업에서 시작한 프로젝트가 3~4년 뒤 포트폴리오의 첫 페이지가 된다.
