## 먼저 알아야 할 것 : 이 수업에서 쓰는 도구가 뭔지

코딩을 전혀 모르는 학생을 위해, 이 수업에서 나오는 단어를 먼저 쉽게 정리한다.

| 단어 | 이게 뭔데? | 비유 |
|---|---|---|
| **Python (파이썬)** | 컴퓨터한테 일을 시키는 언어. 전 세계에서 가장 많이 쓰는 프로그래밍 언어 | 컴퓨터한테 말하는 "외국어" 같은 것. 근데 이 수업에선 AI가 대신 말해줌 |
| **Streamlit (스트림릿)** | 파이썬으로 만든 코드를 "앱 화면"으로 바꿔주는 도구. 버튼, 입력칸, 차트 같은 걸 쉽게 만들어줌 | 코드를 "눈에 보이는 앱"으로 바꿔주는 마법 도구 |
| **바이브 코딩** | AI한테 "이런 거 만들어줘"라고 말로 설명하면, AI가 코드를 만들어주는 방식 | 내가 "이런 집 지어줘"라고 설명하면 AI 건축가가 지어주는 것. 나는 "여기 창문 더 넣어줘"라고 말만 하면 됨 |
| **배포** | 내 컴퓨터에서만 돌아가던 앱을 인터넷에 올려서 다른 사람도 쓸 수 있게 하는 것 | 내 방에 있던 작품을 전시회에 내놓는 것 |
| **JSON (제이슨)** | 데이터를 정리하는 방식. `{"이름": "비빔밥", "별점": 4}` 이런 식 | 엑셀 표를 좀 더 컴퓨터가 읽기 쉽게 적는 방법 |

> 이 단어들을 지금 다 이해할 필요 없다. 수업하면서 자연스럽게 알게 된다.

## 이 수업에서 제일 중요한 것

### "코딩을 배우는 게 아니라, 만드는 과정을 배운다"

AI가 코드를 대신 짜주는 시대가 왔다. 그러면 사람은 뭘 해야 할까?

```
AI가 잘하는 것                    사람이 해야 하는 것
─────────────────────          ─────────────────────
코드 작성                        "뭘 만들지?" 정하기
에러 수정                        "누가 쓸 건데?" 생각하기
반복 작업                        "이거 쓰기 불편한데?" 판단하기
빠른 검색                        "왜 이걸 만들어야 하지?" 이유 찾기
```

> **바이브 코딩** = AI에게 "이런 거 만들어줘"라고 말하고, 나온 결과를 보고, "여기 좀 고쳐줘"라고 다시 말하는 것.
> 코드를 한 글자도 칠 줄 몰라도 된다. **내가 원하는 걸 말로 설명할 줄 알면** 앱을 만들 수 있다.

## 만드는 과정은 딱 4단계다

이 4단계를 한 바퀴 돌려보는 게 이 수업의 진짜 목표다.

```
 1단계. 정하기     "누구한테, 어떤 문제를 풀어줄 건데?"
                    예) "우리 반 친구들이 급식 별점을 매길 수 있는 앱"
                         ↓
 2단계. 그리기     "화면이 어떤 순서로 넘어가?"
                    예) 시작 화면 → 별점 입력 → 결과 차트
                         ↓
 3단계. 만들기     AI에게 설명해서 코드를 받는다 (바이브 코딩)
                    예) "별점을 1~5로 매기는 슬라이더 만들어줘"
                         ↓
 4단계. 고치기     직접 써보고 불편한 곳을 찾아 고친다
                    예) "버튼이 너무 작아" → AI한테 "버튼 크게 해줘"
```

```
       사람이 한다         사람이 한다        AI가 해준다         사람이 한다
       ──────────         ──────────        ───────────         ──────────
       1단계 정하기        2단계 그리기       3단계 만들기         4단계 고치기
```

> 4단계 중 AI가 하는 건 **3단계 하나뿐**이다.
> 나머지 3개는 전부 사람이 한다. 그래서 "코딩 실력"보다 **"생각하는 힘"**이 더 중요하다.

## 서버가 필요할까?

수업 중에 "서버"라는 단어가 나올 텐데, 어려운 게 아니다. 딱 하나만 기억하면 된다.

```
질문 : "이건 나만 쓸 건가, 여러 명이 같이 쓸 건가?"

나만 쓴다                              여러 명이 같이 쓴다
────────                              ──────────────────
→ 서버 필요 없음                       → 서버 필요함
→ 내 컴퓨터에서만 돌리면 끝            → 인터넷에 올려야 함

예) 공부 타이머, 가계부, 게임           예) 설문 조사, 급식 별점
    (내 기록만 있으면 됨)                   (다른 사람 데이터를 모아야 함)
```

> 서버가 뭔지 기술적으로 몰라도 전혀 상관없다.
> **"다른 사람의 데이터를 모아야 하면 서버가 필요하다"** — 이것만 알면 된다.

## 회차별 자세한 설명

### 1회차 : "왜 만드는가" 이해하기 (2시간)

이 시간의 목표 : **"나도 앱을 만들 수 있구나"를 느끼는 것.**
코딩 경험이 전혀 없어도 괜찮다. 이 시간에는 코드를 한 줄도 안 친다.

| 시간 | 뭘 하나 | 코딩 몰라도 되나? |
|---|---|---|
| 0:00~0:20 | **팀 만들기.** 5명이 한 팀. 역할 정하기 (진행자 / 기획 / 화면 / 데이터 / 발표). 서로 이름 익히기 | 전혀 상관없음 |
| 0:20~0:50 | **이야기 시간.** "AI가 코드를 다 짜주면, 사람은 뭘 잘해야 할까?" 같이 생각해보기. "만드는 4단계"를 배운다 | 코딩 얘기 아님 |
| 0:50~1:10 | **토론.** 카카오톡은 서버가 필요할까? 계산기 앱은? → "여러 명이 같이 쓰면 서버가 필요하다"는 기준 세우기 | 의견만 내면 됨 |
| 1:10~1:40 | **라이브 데모.** 선생님이 AI한테 "급식 별점 앱 만들어줘"라고 말한다 → 5분 뒤에 진짜 앱이 나온다 → **"와, 말만 했는데 앱이 나왔어?"** 이 순간이 핵심 | 그냥 구경하면 됨 |
| 1:40~2:00 | **주제 정하기.** 아이디어 10개 중에서 우리 팀 주제 고르기. 한 줄 기획서 쓰기 : "○○가 / ○○ 때문에 불편해서 / ○○를 만든다" | 글 한 줄 쓰는 것 |

> **이 날 핵심 순간** : 선생님이 AI한테 말로 설명만 했는데 앱이 나오는 걸 직접 보는 것.
> "어, 나도 말만 하면 만들 수 있겠는데?" — 이 자신감이 나머지 3일의 연료가 된다.

### 2회차 : "어떻게 흘러가는지" 그리기 + 첫 화면 (2시간)

이 시간의 목표 : **종이에 설계도를 그리고, AI한테 처음으로 "만들어줘"라고 말해보는 것.**

| 시간 | 뭘 하나 | 코딩을 모르면 어떻게 하나? |
|---|---|---|
| 0:00~0:30 | **종이에 화면 그리기.** A4에 네모 칸을 그리고 화살표로 연결한다. "시작 화면 → 입력 화면 → 결과 화면" | 그림 그리는 거다. 코딩 아님 |
| 0:30~0:50 | **앱에 저장할 정보 정하기.** "급식 앱이면 메뉴 이름, 별점, 한줄평이 필요하겠네" → 이걸 정리하는 게 데이터 설계 | 목록 만드는 것 |
| 0:50~1:30 | **처음으로 바이브 코딩!** AI한테 "제목이 있고, 시작 버튼이 있는 화면 만들어줘"라고 말한다 → AI가 코드를 준다 → 그 코드를 복사해서 붙여넣고 실행한다 → 화면이 나온다! → "버튼 색 파란색으로 바꿔줘" 다시 요청 | 선생님이 **한 단계씩 같이 따라가며** 도와줌. 복사/붙여넣기만 할 줄 알면 됨 |
| 1:30~1:50 | **기본 부품 체험.** 버튼 누르기, 선택지 고르기, 슬라이더 밀기, 글 입력하기 — 이 4가지 부품이면 앱 대부분을 만들 수 있다 | AI한테 "버튼 하나 만들어줘"라고 말하면 됨 |
| 1:50~2:00 | **팀 회고.** "오늘 된 것 / 안 된 것 / 다음에 할 것" 3줄만 적기 | 글 쓰는 것 |

> **여기서 깨닫는 것** : "알고리즘"이란 거창한 게 아니다.
> "시작 화면 다음에 뭐가 나오지?" — 이 순서를 정하는 게 알고리즘이다.
> 종이에 네모 그리고 화살표 그은 순간, 이미 알고리즘을 만든 거다.

### 3회차 : 진짜 만들기 + 팀으로 합치기 (2시간)

이 시간의 목표 : **각자 만든 조각을 하나로 합쳐서, 처음부터 끝까지 돌아가게 만드는 것.**

| 시간 | 뭘 하나 | 막히면? |
|---|---|---|
| 0:00~0:50 | **나눠서 만들기.** 화면 흐름도에서 각자 맡은 부분을 AI한테 설명해서 만든다. 화면 담당은 "이 화면 예쁘게 꾸며줘", 기획은 "질문 5개 써줘", 데이터 담당은 "별점 평균 계산해줘" | **AI한테 "이거 어떻게 해?"라고 물어본다.** AI가 답을 모르면 선생님한테 물어본다. 혼자 끙끙거리지 말고 바로 물어보는 게 이 수업의 규칙 |
| 0:50~1:20 | **합치기.** 각자 만든 화면을 하나로 연결한다. "시작 화면에서 버튼 누르면 다음 화면 나오게 해줘"라고 AI한테 말하면 된다 | AI한테 "이 두 화면을 연결해줘"라고 그대로 말하면 됨 |
| 1:20~1:40 | **직접 써보고 고치기.** 앱을 처음부터 끝까지 한 번 써본다. 안 되는 거 목록 만들기 → AI한테 "이거 왜 안 돼?"라고 물어보기 → 고치기 | 안 되는 게 당연하다. **"안 되는 걸 찾아내는 것" 자체가 실력**이다 |
| 1:40~1:50 | **다른 팀한테 보여주기.** 지금까지 만든 거 시연. "이 부분 헷갈려", "여기 좋다" 피드백 듣기 | |
| 1:50~2:00 | **팀 회고.** "내일 꼭 마무리할 것" 목록 | |

> **여기서 배우는 것** : 완벽하게 만드는 사람은 아무도 없다.
> 프로 개발자도 **"일단 만들고 → 써보고 → 고치기"를 계속 반복**한다.
> 이걸 한 번이라도 경험해본 사람과, 안 해본 사람은 완전히 다르다.

### 4회차 : 예쁘게 다듬고, 세상에 내놓기 (2시간)

이 시간의 목표 : **앱을 인터넷에 올리고, 다른 사람 앞에서 발표하는 것.**

| 시간 | 뭘 하나 | 포인트 |
|---|---|---|
| 0:00~0:30 | **다듬기.** "처음 보는 사람이 이 앱 열었을 때, 뭘 해야 하는지 바로 알겠어?" 이 기준으로 점검. 글씨 크기, 버튼 위치, 색깔 조정. AI한테 "이 화면을 더 깔끔하게 바꿔줘"라고 요청 | 예쁜 게 아니라 **"알아보기 쉬운 게"** 좋은 디자인 |
| 0:30~0:50 | **배포.** 앱을 인터넷에 올린다 → URL이 생긴다 → QR코드 만든다 → 옆 팀한테 보내서 진짜로 써보게 한다 | "내가 만든 게 인터넷에 있다!" — **이 순간이 8시간 중 가장 중요** |
| 0:50~1:05 | **발표 준비.** 딱 3가지만 정리 : ① 왜 만들었나 ② 앱 직접 보여주기 ③ 뭘 배웠나 | 외울 필요 없음. 메모 보고 해도 됨 |
| 1:05~1:45 | **팀 발표회.** 각 팀 3분 발표. 다른 팀 앱도 직접 써본다 | 발표 못해도 괜찮음. 앱이 말해줌 |
| 1:45~2:00 | **다음 단계.** 방학 때 프로젝트 2번째 도전 안내. 지금 만든 게 포트폴리오의 시작이라는 이야기 | |

> **여기서 배우는 것** : "만드는 것"과 "세상에 내놓는 것"은 완전히 다르다.
> 다른 사람이 내 앱을 쓰는 걸 보는 순간, "아 이 부분 불편하구나" 또는 "오, 진짜 좋아하네" — 이 감각은 교과서에서 절대 못 배운다.

## 팀 역할 (5명이 하나의 프로젝트를 만든다)

| 역할 | 하는 일 | 쉽게 말하면 |
|---|---|---|
| **PM** (진행자) | 시간 관리, 팀원 의견 정리, "지금 뭐 해야 하지?" 정해주기 | 감독 |
| **기획** | 질문/스토리/콘텐츠 만들기, 한 줄 기획서 관리 | 작가 |
| **화면 담당** | 앱이 보기 좋게 되도록 배치, 색깔, 글씨 다듬기 | 디자이너 |
| **데이터 담당** | 점수 계산, 데이터 저장, 차트 만들기 | 엔지니어 |
| **발표 담당** | 매번 뭘 했는지 기록, 최종 발표 | 기자 |

> 역할은 "책임 영역"이지, **코딩 면제가 아니다.**
> 5명 전원이 AI한테 직접 말해보고, 결과를 보고, 수정 요청하는 경험을 한다.
> "나는 화면 담당이니까 코딩 안 해도 돼" — 이런 건 없다.

## 이 수업은 왜 "바이브 코딩"으로 하는가?

### 기존 코딩 수업 vs 이 수업

| 기존 코딩 수업 | 이 수업 |
|---|---|
| `print("Hello")` 치는 법 배움 | **진짜 돌아가는 앱** 1개 완성 |
| 문법 암기 (변수, 조건문, 반복문) | 만드는 **과정** (정하기→그리기→만들기→고치기) 경험 |
| 정답이 정해진 문제 풀기 | **정답이 없는 문제**를 직접 정의하고 해결 |
| 혼자 하는 숙제 | **5명이 팀으로** 함께 완성 |
| 수업 끝나면 남는 게 없음 | **인터넷에 올라간 앱 URL**이 남음 |
| 3개월 배워도 뭘 만들 수 없음 | **8시간 만에** 앱 하나 완성 |

### AI 시대에 프로젝트를 만드는 방법

```
[과거] 문법 공부 → 코드 타이핑 → 디버깅 → 완성
      (몇 달 걸림. 중간에 대부분 포기)

[지금] 문제 정의 → AI에게 설명 → 결과 확인 → 수정 요청 → 완성
      (몇 시간이면 됨. 코딩을 몰라도 됨)

       사람         사람           사람         사람
                 (AI가 코드를 짜줌)
```

> 달라진 건 "코드를 누가 짜느냐"이고,
> 달라지지 않은 건 **"뭘 만들지 정하는 건 사람"**이라는 것.
>
> 그래서 이 수업은 코드를 가르치지 않는다.
> **"정하고, 그리고, 확인하고, 고치는 과정"**을 가르친다.
> 이 과정을 아는 사람이 AI를 도구로 쓸 수 있는 사람이다.

## 코딩을 전혀 모르는 학생을 위한 Q&A

| 걱정 | 대답 |
|---|---|
| "나 코딩 한 번도 안 해봤는데?" | 이 수업은 코딩을 가르치는 수업이 아니다. AI가 코드를 짜주고, 너는 "뭘 만들지"를 정하는 사람이다. |
| "코드가 뭔지도 모르는데 어떻게 해?" | 코드를 읽을 줄 몰라도 된다. AI한테 한국어로 말하면 된다. "버튼 만들어줘", "색 바꿔줘" 이렇게. |
| "다른 애들은 다 잘할 것 같은데..." | 이 수업에서 제일 중요한 건 코딩 실력이 아니라 "아이디어를 말로 설명하는 능력"이다. 코딩 잘하는 애가 유리한 수업이 아니다. |
| "실수하면 어떡해?" | 실수하는 게 당연하다. 프로 개발자도 매일 실수하고 고친다. "안 되는 걸 발견하는 것" 자체가 실력이다. |
| "팀에서 내가 민폐면?" | 5가지 역할 중에 기획, 발표 같은 건 코딩과 전혀 상관없다. 아이디어를 내거나, 기록하거나, 발표하는 것도 프로젝트에서 엄청 중요한 일이다. |
| "8시간 만에 진짜 앱이 나와?" | 나온다. 화려하지 않아도 "진짜 돌아가는 앱"이 나온다. 그게 이 수업의 포인트다. |

## 평가 방법

### 점수가 아니라 "과정"을 본다

| 보는 것 | 어떻게 확인하나 |
|---|---|
| **기획서** | "누가 / 왜 / 뭘 만드는가"를 한 줄로 정리했는가? |
| **화면 흐름도** | 종이에 그린 설계도가 앞뒤가 맞는가? |
| **중간 과정** | "안 되는 것"을 발견하고 "고치려고 시도"했는가? |
| **완성 앱** | 처음부터 끝까지 한 번은 돌아가는가? |
| **팀 발표** | "왜 → 시연 → 배운 점"을 전달했는가? |

> **완벽하게 만들었느냐를 보는 게 아니다.**
> "4단계를 한 바퀴 돌렸느냐"를 본다.
> 버그가 있어도 괜찮다. "왜 이게 안 되는지 알고 있다"가 더 중요하다.

### 발표는 이렇게 하면 된다

```
3분 발표 = 이 3가지만 말하면 된다 :

  ① 왜 만들었나?     →  "○○가 불편해서 이걸 만들었습니다"
  ② 어떻게 생겼나?   →  앱을 직접 돌려서 보여주기
  ③ 뭘 배웠나?       →  "이게 어려웠는데 이렇게 해결했습니다"

  외울 필요 없다. 메모 보고 해도 된다. 앱이 말해준다.
```

## 이 수업이 끝난 다음에는?

이 수업은 "끝"이 아니라 **"시작"**이다.

```
프로젝트 1 (이 수업, 중2)
  → 8시간 만에 앱 1개 완성
  → "나도 만들 수 있구나" 자신감
       ↓
프로젝트 2 (방학, 중3)
  → 4주간 더 깊이 만들기
  → 친구 20~100명이 진짜로 쓰는 서비스
  → 피드백 받고 고치는 경험
       ↓
프로젝트 3 (고등학교)
  → 3~6개월 제대로 만들기
  → 사용자 500명+
  → 대입 포트폴리오의 핵심 소재
```

> 2032년 대입에서는 "시험 점수"뿐 아니라 **"내가 뭘 만들었고, 어떻게 성장했는가"**를 본다.
> 이 수업에서 시작한 프로젝트가 3~4년 뒤 포트폴리오의 첫 페이지가 된다.
