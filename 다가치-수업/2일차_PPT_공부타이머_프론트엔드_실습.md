## 페이지 4: 프론트엔드 vs 백엔드

### 식당에 비유하면?

| 구분 | 프론트엔드 (오늘) | 백엔드 (다음 시간) |
|---|---|---|
| 비유 | 식당의 인테리어, 메뉴판 | 식당의 주방, 냉장고 |
| 역할 | 사용자가 보고 누르는 화면 | 데이터를 저장하고 처리하는 서버 |
| 기술 | HTML + CSS + JavaScript | Python (Flask) + 데이터베이스 |
| 오늘 방식 | 더미 데이터로 화면만 만든다 | 다음 시간에 진짜 데이터 연결 |

```
┌─────────────────────────────────────────────┐
│              사용자 (브라우저)                │
│   "화면 보여줘!" / "버튼 눌렀어!"            │
└──────────────────┬──────────────────────────┘
                   │
        ┌──────────▼──────────┐
        │   프론트엔드 (오늘)   │  ← HTML, CSS, JS
        │   화면, 버튼, 디자인  │
        └──────────┬──────────┘
                   │
        ┌──────────▼──────────┐
        │  백엔드 (다음 시간)   │  ← Python, Flask
        │  데이터 저장/처리     │
        └─────────────────────┘
```

왼쪽 이미지: 깔끔한 식당 내부 인테리어 (프론트엔드)
오른쪽 이미지: 식당 주방에서 요리하는 모습 (백엔드)

## 페이지 5: 더미 데이터란?

### 가짜 데이터로 화면을 테스트한다

**더미 데이터(dummy data)** = 화면이 잘 보이는지 확인하기 위해 미리 만들어 놓은 가짜 데이터

| 구분 | 더미 데이터 (오늘) | 진짜 데이터 (다음 시간) |
|---|---|---|
| 수학 25분 | 미리 코드에 적어둔 숫자 | 타이머로 실제 잰 시간 |
| 영어 30분 | 화면 테스트용 가짜 | 서버에 저장된 진짜 기록 |
| 총 3시간 | 확인용 숫자 | 자동 계산된 합계 |
| 저장 방식 | JavaScript 변수 | 서버 파일/DB |

```
┌──────────────┐         ┌──────────────┐
│  오늘 (더미)  │         │ 다음 시간 (진짜) │
│              │         │              │
│  JS 변수에    │  ──▶   │  서버에 저장   │
│  가짜 숫자    │ 교체!   │  진짜 데이터   │
│              │         │              │
│  화면은 동일! │         │  화면은 동일!  │
└──────────────┘         └──────────────┘
```

비유: 가구 매장의 "모델 하우스" — 실제 살지는 않지만 어떻게 보이는지 확인할 수 있다.

## 페이지 8: 기획의 순서

```
  ① 페르소나        ② 벤치마킹        ③ 유저 시나리오      ④ 개발
┌───────────┐   ┌───────────┐   ┌───────────────┐   ┌──────────┐
│ 누가 쓸까? │──▶│ 다른 앱은  │──▶│ 어떤 순서로    │──▶│ 그걸     │
│           │   │ 어떻지?    │   │ 쓸까?         │   │ 만들자!  │
└───────────┘   └───────────┘   └───────────────┘   └──────────┘
```

| 단계 | 기획 없이 | 기획하고 나서 |
|---|---|---|
| 기능 | "뭐부터 만들지?" 고민만 | "민수가 과목을 먼저 고르니까 드롭다운부터" |

| 디자인 | "어떻게 하지?" 막막함 | "민수는 심플한 걸 좋아해" → 방향이 명확 |
| 결과 | 시간만 날림 | 효율적으로 완성 |

## 페이지 9: STEP 1 — 페르소나란?

### 가상의 사용자 캐릭터를 만든다

**페르소나** = 우리 앱을 쓸 **가상의 사용자 캐릭터**

게임 캐릭터를 만들듯이, 우리 앱을 쓸 사람의 캐릭터를 만드는 것!

```
              ┌──────────────┐
              │   페르소나     │
              └──────┬───────┘
        ┌────────┬───┴───┬────────┐
        ▼        ▼       ▼        ▼
   ┌────────┐┌───────┐┌───────┐┌────────┐
   │이름/나이││ 상황  ││ 고민  ││ 원하는 것│
   │        ││시험?  ││집중   ││시간관리 │
   │        ││자습?  ││못함?  ││동기부여 │
   └────────┘└───────┘└───────┘└────────┘
```

| 페르소나 항목 | 질문 | 예시 |
|---|---|---|
| 이름 / 나이 | 누구? | 김민수, 중2 |
| 상황 | 언제 쓰나? | 시험 2주 전, 자습 시간 |
| 고민 | 뭐가 불편하나? | 시간이 얼마나 갔는지 모름 |
| 원하는 것 | 뭘 해결하고 싶나? | 과목별 시간 측정 |

배경 이미지: 게임 캐릭터 생성 화면처럼 프로필을 만드는 일러스트

## 페이지 10: 페르소나가 왜 필요한가?

### 있을 때 vs 없을 때

| 질문 | 페르소나 없이 | 페르소나 있으면 |
|---|---|---|
| 누가 쓰지? | "모르겠는데..." | "민수가 시험 기간에 쓸 거야" |
| 기능을 뭘 넣지? | "이것저것 다?" | "민수는 과목별 시간이 필요해" |
| 디자인은? | "예쁘게?" | "민수는 심플한 게 좋대" |
| 어디서부터? | "일단 해보자..." | "과목 선택부터 만들자" |

```
  페르소나 없음                    페르소나 있음
┌─────────────┐              ┌─────────────┐
│  ???        │              │  김민수      │
│  뭘 만들지?  │              │  중2, 시험전  │
│  어떻게?     │              │  심플 좋아함  │
│  ...막막    │              │  과목별 필요  │
└─────────────┘              └──────┬──────┘
       │                           │
       ▼                           ▼
   시간만 날림                기능이 자연스럽게 나옴
```

> 사용자를 먼저 정해야 뭘 만들지 알 수 있다!

```

├──────────────────────────────────────────┤
```

| "심플하게!" | 깔끔한 디자인 | 필수 |

이미지: 책상 앞에서 공부하는 중학생 일러스트

## 페이지 13: STEP 2 — 벤치마킹이란?

### 잘 만든 앱을 구경하고 배운다

**벤치마킹** = 다른 사람이 잘 만든 것을 **구경하고 배우는 것**

비유: 요리사가 새 메뉴를 만들기 전에 맛집을 가보는 것과 같다.

```
              ┌────────────┐
              │  벤치마킹   │
              └──────┬─────┘
        ┌────────────┼────────────┐
        ▼            ▼            ▼
  ┌──────────┐ ┌──────────┐ ┌──────────┐
  │ 잘 된 점  │ │ 아쉬운 점 │ │ 우리 앱에 │
  │ 찾기     │ │ 찾기     │ │ 적용     │
  │          │ │          │ │          │
  │ "이건    │ │ "이건 더  │ │ "우리는  │
  │  따라하자"│ │ 잘 만들자"│ │ 이렇게!" │
  └──────────┘ └──────────┘ └──────────┘
```

| 단계 | 질문 | 행동 |
|:---:|---|---|
| 1 | 뭐가 잘 되어 있나? | 좋은 점 기록 |
| 2 | 뭐가 아쉬운가? | 개선할 점 기록 |
| 3 | 우리 앱에 어떻게 적용? | 기능 목록 정리 |

## 페이지 14: 타이머 앱 벤치마킹

### 3가지 앱을 비교해보자

| 항목 | 뽀모도로 타이머 | Forest (집중앱) | 열품타 |
|---|---|---|---|
| 핵심 기능 | 25분/5분 자동 반복 | 집중하면 나무 성장 | 순공시간 측정 |
| 잘한 점 | 시간 관리가 체계적 | 재미 요소가 있다 | 정확한 시간 측정 |
| 아쉬운 점 | 과목 구분이 없다 | 기록 확인이 불편 | 디자인이 복잡 |
| 우리가 배울 것 | 과목별로 만들자 | 기록을 바로 보여주자 | 심플하게 만들자 |

**벤치마킹 결론 — 우리 앱의 방향:**

| 우리 앱이 가져갈 것 | 참고한 앱 |
|---|---|
| 과목별 시간 관리 | 뽀모도로 (시간 관리) + 우리만의 과목 분류 |
| 기록을 바로 보여주기 | Forest의 아쉬운 점 개선 |
| 심플한 디자인 | 열품타의 아쉬운 점 개선 |

이미지: 3개 앱의 스크린샷을 나란히 배치 (뽀모도로, Forest, 열품타)

## 페이지 16: STEP 3 — 유저 시나리오란?

### 사용자가 앱을 쓰는 순서를 상상한다

**유저 시나리오** = 사용자가 앱을 **실제로 쓰는 순서**를 미리 상상해보는 것

비유: 드라마 대본처럼 "김민수가 앱을 열면 → 이걸 하고 → 저걸 하고..."를 적는 것

| 비교 | 시나리오 없이 | 시나리오 있으면 |
|---|---|---|
| 시작 | "일단 만들자!" → 뭐부터? | "민수가 처음에 과목을 고른다" → 드롭다운 |
| 순서 | 만들고 보니 이상하다 | 사용 순서대로 자연스럽다 |
| 화면 | 몇 개 필요한지 모르겠다 | 시나리오 한 단계 = 화면 하나 |
| 결과 | 중간에 다시 만든다 | 한 번에 제대로 만든다 |

```
  시나리오 = 사용자의 "여정 지도"

  ┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐
  │ 시작 │──▶│ 선택 │──▶│ 사용 │──▶│ 결과 │──▶│ 확인 │
  │      │   │      │   │      │   │      │   │      │
  │앱열기│   │과목  │   │타이머│   │기록  │   │통계  │
  └──────┘   └──────┘   └──────┘   └──────┘   └──────┘
    화면1      화면2      화면3      화면4      화면5
```

## 페이지 17: 김민수의 유저 시나리오

### 민수가 앱을 쓰는 8단계

| 단계 | 민수가 하는 일 | 필요한 화면/기능 |
|:---:|---|---|
| 1 | 앱을 연다 (브라우저에서 접속) | 메인 화면 |
| 2 | 과목을 선택한다 (수학, 영어...) | 과목 드롭다운 |
| 3 | 타이머 시작 버튼을 누른다 | 시작 버튼 |
| 4 | 공부한다 (타이머가 돌아간다) | 카운트다운 표시 |
| 5 | 타이머 종료! "수고했어!" 메시지 | 완료 메시지 |
| 6 | 기록이 자동 저장된다 | 저장 기능 |
| 7 | 오늘의 기록을 확인한다 | 막대 그래프 |
| 8 | 대시보드에서 통계를 본다 | 대시보드 화면 |

```
 ①앱 열기 ──▶ ②과목 선택 ──▶ ③시작! ──▶ ④공부 중...
                  ▲                           │
                  │                           ▼
                  │                      ⑤타이머 종료
                  │                      "수고했어!"
                  │                           │
                  │         YES               ▼
              더 공부? ◀────────── ⑥기록 저장됨
                  │
                  │ NO
                  ▼
         ⑦오늘 기록 확인 ──▶ ⑧대시보드 통계
```

## 페이지 18: 시나리오에서 오늘 만들 것

### 오늘 만들 것 vs 다음 시간에 만들 것

| 시나리오 단계 | 필요한 기능 | 오늘 | 방식 |
|---|---|:---:|---|
| 1~3. 앱 열기 + 과목 + 시작 | 타이머 + 드롭다운 | O | 더미 |
| 4~5. 타이머 동작 + 종료 | 카운트다운 + 메시지 | O | 실제 동작 |
| 6. 기록 저장 | 저장 메시지 | O | 더미 (메시지만) |
| 7. 오늘 기록 확인 | 막대 그래프 | O | 더미 데이터 |
| 8. 대시보드 통계 | 주간/월간 화면 | O | 이미 있음! |

```
┌────────────────────────────────────────────────┐
│              오늘 만드는 것 (프론트엔드)          │
│                                                │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐     │
│  │ 타이머   │  │ 과목선택  │  │ 기록표시  │     │
│  │ 화면     │  │ 드롭다운  │  │ 막대그래프│     │
│  │ (실제)   │  │ (더미)   │  │ (더미)   │     │
│  └──────────┘  └──────────┘  └──────────┘     │
│                                                │
│  ┌──────────────────────────────────────┐      │
│  │ 대시보드 화면 (이미 만들어져 있음!)    │      │
│  └──────────────────────────────────────┘      │
└────────────────────────────────────────────────┘
```

> "더미" = 화면은 보이지만 진짜 저장/계산은 안 됨. 다음 시간에 백엔드를 연결하면 진짜로 동작!

## 페이지 25: 첫 번째 코드 — app.py

### 기본 서버 코드

```python
from flask import Flask, render_template

app = Flask(__name__)

@app.route('/')
def home():
    return render_template('index.html')

if __name__ == '__main__':
    app.run(debug=True)
```

| 줄 | 코드 | 뜻 | 비유 |
|:---:|---|---|---|
| 1 | `from flask import Flask` | Flask 도구 가져오기 | 연장통 열기 |
| 3 | `app = Flask(__name__)` | 웹 서버 하나 만들기 | 가게 차리기 |
| 5 | `@app.route('/')` | 메인 주소로 오면 | 정문으로 들어오면 |
| 6~7 | `def home(): return ...` | index.html을 보여준다 | 메뉴판 보여주기 |
| 9~10 | `app.run(debug=True)` | 서버를 켠다 | 가게 오픈! |

> 외울 필요 없다! 어떤 역할인지만 이해하면 된다.

## 페이지 31: 대시보드 서버 띄우기

### 두 번째 app.py — 대시보드 서버

```python
from flask import Flask, send_file

app = Flask(__name__)

@app.route('/')
def dashboard():
    return send_file('study-timer-dashboard.html')

if __name__ == '__main__':
    app.run(debug=True, port=5001)
```

| 코드 | 기본 app.py와 차이점 | 이유 |
|---|---|---|
| `send_file(...)` | `render_template` 대신 사용 | HTML을 그대로 보내기 위해 |
| `port=5001` | 기본은 5000 | 두 서버를 동시에 실행하려고 |

**두 서버를 동시에 실행할 수 있다!**

```
  내 컴퓨터 (서버 2개 동시 실행)
┌────────────────────────────────────────────┐
```

## 페이지 34: 프롬프트를 분석해보자

### 좋은 프롬프트의 구조

| 프롬프트 부분 | 역할 | 왜 중요한가 |
|---|---|---|
| "과목 선택 기능을 추가해줘" | 전체 목표 | AI가 뭘 만들지 안다 |
| "드롭다운(select)" | 구체적 UI 방식 | 어떤 형태인지 명확 |
| "과목 목록: 5개" | 정확한 데이터 | 추측 없이 정확하게 |

| "프론트엔드만 구현" | 범위 제한 | 불필요한 것 안 만듦 |

```
  좋은 프롬프트 공식:

  ┌──────────┐   ┌──────────┐   ┌──────────┐
  │ 무엇을    │ + │ 어떻게    │ + │ 제약 조건 │
  │          │   │          │   │          │
  │ "과목 선택│   │ "드롭다운 │   │ "프론트만 │
  │  추가해줘"│   │  5개 과목"│   │  더미데이터│
  └──────────┘   └──────────┘   └──────────┘
```

| 나쁜 프롬프트 | 좋은 프롬프트 | 차이 |
|---|---|---|
| "과목 기능 넣어줘" | "드롭다운으로 5개 과목 선택" | 구체적 |
| "예쁘게 만들어줘" | "과목마다 색깔 다르게, 파랑/주황/..." | 수치 제시 |
| "타이머 고쳐" | "타이머 위에 과목 이름을 30px로 표시" | 위치+크기 |
